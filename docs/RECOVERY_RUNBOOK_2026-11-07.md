# Vault v2: trusted one-case recovery runbook (sandbox validation)

This runbook covers only a future, separately authorized incident on a **new dedicated Vault v2 account**. The local `spike/recovery-prototype/` binaries are fixed to `*.test.near` sandbox accounts and **must never be deployed to Testnet**. The historical single-owner account is incompatible. No live account, key, transaction or Testnet receipt was used in this validation.

## Evidence gate before building an incident WASM

1. Stop agent execution and notify owners. Record contract account, original code hash, owner, immutable payment ID or withdrawal nonce, recipient, amount, policy version and window, current `get_vault`, `get_payment_details` or `get_pending_withdrawal`, account balance, storage usage and access-key list at FINAL. Do not release any pending amount while the outcome is unknown.
2. Query the initiating transaction with `tx_status` and `wait_until: "FINAL"` from **two separately operated Testnet RPC services**: [FASTNEAR `https://test.rpc.fastnear.com`](https://docs.near.org/api/rpc/providers) and [NEAR archival `https://archival-rpc.testnet.near.org`](https://docs.near.org/api/rpc/providers). A third option is the separately listed dRPC `https://near-testnet.drpc.org`. These are independent operators, but both report the same NEAR chain; they are not independent cryptographic proofs. Verify their current operation and archival coverage at incident time. If one is unavailable, stale, omits receipts, or disagrees, stop. Two hostnames backed by the same operator, explorer, proxy or node do **not** satisfy this gate. Do not infer a failure from an RPC error or timeout.
3. For each source, use the same request body, replacing only the endpoint: `{"jsonrpc":"2.0","id":"recovery-review","method":"tx_status","params":{"tx_hash":"<initiating-hash>","sender_account_id":"<signer>","wait_until":"FINAL"}}`. [NEAR transaction RPC](https://docs.near.org/api/rpc/transactions) says `FINAL` includes refund receipts; on a node without `tx_status`, use documented `EXPERIMENTAL_tx_status` and record that substitution. Save the **full raw responses** and their SHA-256 digests, including transaction, receipt bodies, outcomes and block references. The tx hash is a lookup key, never an on-chain proof.
4. Both reviewers independently match: successful initiating `execute_payment(owner,id)` or `withdraw(amount)` receipt and operation log; Promise transfer receipt receiver/deposit and outcome; callback receipt failure; refund receipt if transfer failed; current still-pending state. Check account balance deltas where available. The transaction's aggregate failure status alone is insufficient. Ensure every earlier in-flight operation is FINAL, no previous recovery occurred, and the expected code hash and other Vaults are unchanged. Any missing or ambiguous edge leaves the operation locked.
5. One operator and one independent reviewer sign a case manifest with evidence digests and a single classification: **SUCCESS** clears pending without refund; **FAILURE** clears pending and credits exactly the original amount once. No classification means no recovery. The FullAccess key holder is a trusted upgrade administrator with unrestricted code deployment power; keep that key outside the agent runtime and repository.

## Candidate upgrade and execution gates

1. Replace the sandbox-only constants in a **separate incident build**, including the exact contract, owner, operation ID or nonce, amount, recipient, state version/window and reviewed evidence digest. Compile exactly one outcome. The method accepts no caller-supplied hash, recipient, amount or outcome and creates no transfer Promise. Preserve `Contract`, `Vault`, `Payment` Borsh fields and the `b"v"` map prefix. `spike/recovery-prototype/check_layout.py` is a source-layout check; sandbox upgrade/restore must also verify actual state.
2. Freeze all ordinary mutation methods in the temporary artifact while retaining private callbacks. Reproduce the target outcome and opposite outcome with forced callback failure in sandbox, then test wrong owner, amount, ID, foreign caller, repeat recovery, freeze, foreign Vault, balance, storage, gas and exact normal-WASM restore. Review candidate SHA-256 and NEAR code hash separately from the normal artifact. Measure current protocol storage price and account balance; a code-size change may lock or release storage stake. A failed candidate test or insufficient storage/gas is a stop condition.
3. Immediately before any **separately authorized** Testnet deploy, repeat both FINAL RPC and state/key/code-hash queries. Do a read-only preflight for the incident artifact and account, inspect exact unsigned deploy/recovery/restore payloads, and obtain explicit owner authorization for each real action. The existing `spike/preflight_deploy.py --artifact-only` checks only the normal WASM and does not authorize or validate an incident upgrade.
4. After deploy, verify FINAL code bytes/hash and unchanged Borsh state; call fixed `recover_case` once from the contract-account FullAccess signer; verify FINAL receipt, status, `available`, `pending`, global solvency, recipient balance and other Vaults. A second call must fail. Restore the reviewed normal WASM and verify its exact code hash, state, storage and replay rejection. If any step disagrees, stop and preserve evidence; never guess a compensating refund.

## Reproduce this local validation

From the repository root on Windows, run `powershell.exe -NoProfile -ExecutionPolicy Bypass -File spike/recovery-prototype/build-fixtures.ps1`. In WSL Ubuntu, run `bash spike/run_recovery_sandbox.sh` (the runner uses the cached local `near-sandbox` binary). `python spike/recovery-prototype/artifact_hashes.py` prints separate artifact hashes; `python spike/preflight_deploy.py --artifact-only` checks the pinned normal WASM without network. The tests create only sandbox accounts. The test runner obtains receipt outcomes directly from the local sandbox execution; it does **not** depend on either external RPC being available. For a real incident, unavailable external receipts are a stop condition, not a reason to infer failure.
