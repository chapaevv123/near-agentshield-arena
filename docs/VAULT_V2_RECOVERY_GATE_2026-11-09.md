# Vault v2: pending evidence and recovery gate

This is a design and test gate for the existing shared Vault v2. It authorizes no Testnet transaction, upgrade, key use or automatic refund. The current deployed contract has payment statuses 0/1/2/3/4/5; **UNKNOWN** is an off-chain evidence state, not a new Borsh variant. A local database may cache observations but must never decide whether tokens moved.

## State and evidence

| Evidence state | Required evidence | Allowed action |
| --- | --- | --- |
| UNKNOWN | Missing, non-FINAL, stale, conflicting or incomplete receipts; missing initiating hash; or chain/code/operation mismatch | Keep on-chain `status=3` and funds reserved. No replay, refund or settlement override. Re-query and escalate. |
| PENDING | FINAL initiating `execute_payment`/`withdraw` receipt created the exact transfer, but the complete outcome chain is not yet independently classified | Keep on-chain pending. Do not use a timeout as proof of failure. |
| SETTLED | Two independent FINAL RPC responses agree on successful exact transfer receipt and failed callback, with current on-chain target still pending; or ordinary callback already finalized status 4 | For callback failure only: incident-specific reviewed success recovery clears pending and sets status 4, **without** crediting available or creating a transfer. |
| FAILED | Two independent FINAL RPC responses agree on failed exact transfer receipt, refund receipt where applicable, failed callback and still-pending on-chain target; or ordinary callback already finalized status 5 | For callback failure only: incident-specific reviewed failure recovery clears pending and restores available exactly once. It creates no transfer. |

The two RPC services must be separately operated and agree on the same transaction, receipt IDs, receipt bodies, outcomes and FINAL block references. Verify chain, contract account, code hash, signer, method and arguments, operation log, recipient, amount, payment ID or withdrawal nonce, policy version/window, target status and all unrelated pending operations. Follow the receipt graph from the successful initiating call to the transfer and callback. A top-level transaction failure, timeout, absent log, browser cache or local database row alone cannot classify the transfer. An RPC error always maps to UNKNOWN. Record raw responses and SHA-256 digests; reviewers independently approve the exact classification before any incident build.

## Recovery transition and migration boundary

The existing sandbox-only prototype in `spike/recovery-prototype/` proves a *given* payment classification can be applied once after a callback failure. Its hard-coded `*.test.near` manifest is **not** a deploy candidate and cannot authenticate historical receipts. The normal contract remains unchanged. No persistent enum or layout migration is needed for this one-case model: preserve all `Contract`, `Vault`, `Payment` Borsh fields and order and the `LookupMap` prefix `b"v"`. Any future persistent `UNKNOWN/PENDING/SETTLED/FAILED` on-chain state instead requires a separate versioned Borsh migration specification and tests before deployment.

For a real incident, compile a new temporary, state-compatible WASM containing **one immutable reviewed case**: exact contract and old code hash, owner, payment ID or withdrawal nonce, recipient, amount, policy/window, initiating/transfer/callback receipt IDs, FINAL block references, evidence digest and one classified outcome. It must freeze new outgoing operations, preserve ordinary callbacks, require contract-self predecessor for recovery, compare manifest against still-pending state, and consume the record exactly once. Before recovery, wait for every existing in-flight operation to reach FINAL and recheck code/state/keys and evidence from both RPCs. On successful transfer, clear pending without refund; on failed transfer, clear pending and credit available once. For withdrawals, remove only the exact nonce. Never schedule a new transfer or accept caller-supplied outcome/hash. A late callback or repeated recovery must reject. Restore the reviewed normal WASM after independent review of the recovery receipt. The FullAccess administrator remains a trusted root, so every upgrade requires separate owner authorization.

If the outcome remains UNKNOWN, no recovery method is called. This may leave funds locked, but it prevents a second payout when the first transfer could have succeeded. No trustless automatic recovery is possible with the current contract state: successful and failed transfers followed by failed callbacks leave the same on-chain pending record.

## Reproducible local evidence and gaps

The Linux CI workflow `.github/workflows/multitenant-spike-sandbox.yml` pins Rust 1.99.0, `near-sdk` 5.30.0 through the lockfiles, `near-workspaces` 0.24.0 through the sandbox lockfile, and the reviewed normal WASM SHA-256. It builds normal, fault-callback and five sandbox-only recovery fixtures, then runs unit/integration, normal WASM, callback-fault and recovery-upgrade suites. The added `build-fixtures.sh` is the Linux counterpart to the existing PowerShell fixture builder. A Linux runner needs a working Rust toolchain with `wasm32-unknown-unknown`, Python 3, C build tools, enough free disk/RAM, outbound access for locked Cargo dependencies and near-sandbox binary download, and permission to start local processes and bind loopback ports. It needs no NEAR Testnet key or RPC. `NEAR_SANDBOX_BIN_PATH` may point to a trusted preinstalled compatible sandbox binary; otherwise near-workspaces obtains its default binary.

The local Windows attempt is blocked before Ubuntu starts: both `wsl.exe -d Ubuntu -- true` and `wsl.exe --status` return `E_ACCESSDENIED` at service/distro enumeration. The lower-level Windows policy or service cause is unknown. Docker CLI exists, but the daemon pipe is absent; it is not an available Linux alternative in this session. Do not change host security settings to work around this. The workflow is prepared locally and has not been published or run; therefore fresh WASM sandbox, fault-injection and recovery results remain BLOCKED. Existing historical sandbox results in `RECOVERY_RUNBOOK_2026-11-07.md` are separate evidence.

Before any real recovery, expand isolated sandbox coverage for withdrawals, late callbacks, unrelated pending operations and window rollover, compare candidate/normal code hashes and storage/gas, and obtain two-RPC FINAL evidence for the actual case. Unknown or contradictory evidence is a permanent stop condition until resolved. Never use the current settled `demo-1` as a recovery case.
